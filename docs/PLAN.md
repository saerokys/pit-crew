# Pit Crew 개발 계획 (PLAN)

기준 문서: 「Pit Crew 기획서 및 MVP 상세 정의서」 v0.2, `CLAUDE.md`, `docs/sdk/*.md`
이 문서는 **무엇을 어떤 순서로 만들지**만 정한다. 화면별 동작과 확인 기준은 `docs/SPEC.md`를 따른다.

## 1. 진행 원칙

- 한 번에 **Phase 하나**만 진행한다. 여러 Phase를 한꺼번에 만들지 않는다.
- Phase 안에서도 **한 화면, 한 기능**씩 만든다. 변경 후 반드시 **빌드 → 에뮬레이터 확인** 후 다음으로 넘어간다.
- 확인에 실패하면 다음으로 넘어가지 않고 현재 Phase만 고친다.
- Phase를 시작하기 전에 Claude Code는 (1) 바꿀 파일 목록, (2) 사용자가 해야 할 일이나 줘야 할 값, (3) 확인 방법을 먼저 말하고 "진행" 답을 기다린다.
- 새 SDK(FusedLocation, TTS, STT, NaviHelper)는 해당 Phase에서 **에뮬레이터에서 동작하는 최소 호출 하나**부터 만든다. 동작하지 않으면 그 사실을 `docs/PROGRESS.md`에 기록하고 해당 기능을 "확인 불가"로 처리한다.
- 계획에 없는 기능은 추가하지 않는다. 필요해 보이면 멈추고 먼저 묻는다.
- 커밋은 Phase 안에서 작은 단위로, 메시지에 화면 ID를 쓴다. 예: `SC-100 홈 화면 레이아웃`
- Phase가 끝나면 `docs/PROGRESS.md`에 완료한 것과 다음 할 일을 남기고, README의 "구조" 절을 갱신한다.
- 권장 모델: 일반 개발은 Sonnet(Medium), 원인을 모르는 오류 분석은 High.

## 3. Phase별 계획

### Phase 0. 개발 환경 정리

- 목표: 깨끗한 상태에서 시작한다.
- 작업
  1. 임시 화면 크기 측정 코드(`TEMP-WINSIZE`)를 제거하고 빌드가 되는지 확인한다.
  2. 샘플 앱의 제어(set) 호출과 "Apply change", 리플렉션 탐색 기능이 앱의 어느 화면에 연결되어 있는지 목록으로 보고한다. 삭제는 하지 않고, 개발자 도구 화면으로 분리해 홈에서 직접 연결하지 않는 방법을 제안한다.
  3. 매니페스트에 읽기 권한만 있는지 다시 확인한다(CONTROL_* 없음).
  4. `.gitignore`를 확인한다(`build`, `.gradle`, `.idea`, `local.properties`, 키·토큰 파일).
- 확인: Build > Compile All Sources 성공, 에뮬레이터에서 앱 실행.
- 완료 조건: 위 4개를 보고받고 사용자가 확인.

### Phase 1. 공통 틀

- 목표: 모든 화면이 같은 모양을 쓰도록 기반을 만든다.
- 작업
  1. `docs/design/tokens.md` 값으로 테마(색, 글자 크기, 모서리, 버튼 높이)를 만든다. tokens.md가 아직 없으면 임시 값을 쓰고 표시해 둔다.
  2. 공통 컴포넌트: 상단 바(앱 이름, 단계 n/7, "가상 차량 값" 배지), 하단 바([이전] [다음]), 큰 버튼, 체크 항목, 카드, 상태 배지(정상/주의/긴급/확인 불가).
  3. 화면 이동 구조(사고 모드 흐름과 홈)를 만든다.
- 확인: 샘플 화면 하나에 컴포넌트를 배치해 에뮬레이터에서 크기와 대비를 눈으로 확인한다.
- 완료 조건: 버튼 높이와 글자 크기가 규칙(14번: 큰 터치 영역, 고대비, 짧은 문구)을 지킨다.

### Phase 2. SC-000, SC-100

- 목표: 앱을 켜면 차량 연동을 초기화하고 홈이 보이며, "사고가 났어요"로 사고 모드에 들어간다.
- 작업
  1. SC-000: Vehicle SDK 초기화와 5개 기능(문, 창문, 배터리, 주행 거리, 방향지시등)의 지원 여부 확인. 결과를 세 상태(읽을 수 있어요 / 이 차량에서는 지원하지 않아요 / 확인하지 못했어요)로 보관한다. 읽기 호출은 Phase 4에서 만든다.
  2. SC-100: 홈(큰 버튼 4개, 연동 상태 한 줄, 가상 차량 값 배지, 하단 안내).
- 규칙: 초기화가 실패해도 홈으로 이동하고 차량 연동만 끈다. 앱이 종료되지 않는다. 앱을 닫을 때 SDK를 해제한다.
- 확인: 각 버튼이 해당 화면(아직 없으면 자리표시 화면)으로 이동한다. 연동 상태 한 줄이 지원 확인 결과를 반영한다.
- 완료 조건: 디자인 PNG(`SC-100.png`)와 비교해 배치가 같다.

### Phase 3. 사고 모드 체크리스트 흐름

- 목표: 정차 확인부터 현장 기록 안내까지 단계가 이어진다.
- 작업: SC-200(정차 확인, 사용자 확인으로만 판단), SC-210(체크리스트 템플릿), SC-220(부상 확인), SC-221(긴급 안내), SC-230(현장 기록 안내: 촬영 항목 체크, 음성 메모 카드는 비활성 상태), SC-240(상대방 정보 확인: 체크만, 입력·저장 없음).
- 규칙: 정차 여부는 속도·기어를 읽지 않는다. 119는 안내만 하고 전화를 걸지 않는다. 다음 버튼은 체크를 다 하지 않아도 누를 수 있다.
- 확인: 처음부터 끝까지 [다음]으로 이동, [이전]으로 복귀, 부상 "있어요/모르겠어요" 선택 시 SC-221을 거친다.
- 완료 조건: 화면 하나씩 PNG와 비교.

### Phase 4. SC-250 차량 상태 읽기

- 목표: 차량에서 읽은 값을 한 화면에 기록한다. 이 앱이 차량 전용이라는 점을 보여 주는 핵심 화면.
- 작업: Door Position, Window Position, EV Battery SoC, Distance Driven, Turn Signal을 읽기만 한다. [다시 읽기] 버튼.
- 규칙: 값을 읽기 전에 capability 확인. 모든 호출은 예외를 잡고 실패하면 "확인 불가". 리스너는 한 번만 등록하고 화면을 떠날 때 해제. 검증된 영역만 사용(CLAUDE.md 5번, 검증 기록 참조).
- 확인: 에뮬레이터 Virtual Console에서 값을 바꾸고 [다시 읽기]로 화면이 바뀌는지 확인. 값이 없을 때 앱이 종료되지 않고 "확인 불가"가 보이는지 확인.
- 완료 조건: 5개 값 모두 읽힘 또는 "확인 불가", 화면 이탈 후 재진입 시 중복 등록 오류 없음.

### Phase 5. SC-260 접수 요약

- 목표: 보험사 통화 때 이 화면을 보고 그대로 말할 수 있다.
- 작업: 사고 시각, 장소(주소 자리는 비워 두고 "확인 불가" 또는 숨김), 다친 사람, 차량 상태, 안내 이행 요약. "참고용" 문구.
- 확인: Phase 3~4에서 입력·읽은 값이 그대로 요약에 나타난다.
- 완료 조건: 법적 판단이나 과실 판단 문구가 없다.

### Phase 6. SC-300, SC-400

- 목표: 평소에도 쓰는 기능과 투명성 화면.
- 작업: SC-300 출발 전 점검(문, 창문, 배터리, 방향지시등 요약), SC-400 연동 상태(읽을 수 있는 항목 목록).
- 확인: 문을 연 상태/닫은 상태에서 SC-300 요약이 바뀐다. SC-400은 실제 읽기 성공 여부를 반영한다.
- 완료 조건: **P0 전체 완료.** 이 시점에 시연 영상용 흐름(SC-100 → 200 → 250 → 260)을 한 번 녹화해 본다.

### Phase 7. SC-205 권한·동의와 위치

- 목표: 위치·음성·네트워크를 사용자가 직접 켠 경우에만 쓴다.
- 작업
  1. SC-205 스위치 3개(기본 꺼짐), 설정 저장.
  2. FusedLocation: `isSupported()` → `initialize()` → `getLastKnownLocation()` 순서로 사고 모드 시작 시 1회만. 최소 호출 하나로 먼저 에뮬레이터 동작을 확인한다.
- 규칙: 꺼져 있어도 사고 모드는 끝까지 진행된다. 위치가 없으면 "확인 불가".
- 확인: 스위치 켬/끔에 따라 SC-221, SC-250, SC-260의 위치 카드가 나타나거나 숨는다. 에뮬레이터에서 위치가 오지 않으면 그 사실을 `docs/PROGRESS.md`에 기록한다.
- 완료 조건: 위치 값이 오든 안 오든 앱이 멈추지 않는다.

### Phase 8. 주소 변환 (Nominatim)

- 목표: 좌표를 주소 문장으로 바꿔 보여 준다.
- 작업: 키가 필요 없는 요청만 사용, 3초 안에 응답이 없으면 끊고 "확인 불가". 네트워크 스위치가 켜져 있고 위치가 있을 때만 호출.
- 규칙: 키·이메일을 코드에 넣지 않는다. 사용 정책이 요구하는 요청 헤더(앱 이름 등)는 일반 이름만 쓰고 개인 이메일은 넣지 않는다.
- 확인: 정상 응답, 네트워크 끊김, 3초 초과 세 경우 모두 앱이 계속 동작한다.

### Phase 9. 음성 안내 (TTS)

- 목표: SC-210 등에서 [소리로 듣기]를 누르면 안내를 읽어 준다.
- 작업: `Mode.ON_DEVICE`, `Locale.KOREA`. 최소 호출 하나(한 문장)로 에뮬레이터 동작과 한국어 지원을 먼저 확인.
- 규칙: 자동 재생 금지, 사용자가 SC-205에서 음성을 허용하고 버튼을 누를 때만 재생. 화면을 떠날 때 `stop()`과 해제.
- 확인: 재생/중단/오류 시 버튼 상태. 동작하지 않으면 버튼을 비활성화하고 기록.

### Phase 10. SC-270 종료와 기록 패키지

- 목표: 사고 대응을 마치고 기록을 저장하거나 저장하지 않고 종료한다.
- 작업: 요약 한 줄, [기록 저장] [저장하지 않고 종료], 저장은 이 기기에만, 삭제 가능. 기록 패키지 항목: 사고 시각, 위치·주소(있으면), 차량 상태, 안내 이행.
- 규칙: 상대방 정보, 사진, 차대번호는 저장하지 않는다. 사용자가 저장을 고른 경우에만 저장.
- 확인: 저장 후 앱 재실행 시 기록이 남고, 삭제하면 사라진다.
- 완료 조건: **P1-A 완료.**

### Phase 11. 날씨와 음성 메모

- 날씨(Open-Meteo): 키 없이, 3초 제한, 실패 시 "확인 불가". 좌표가 있고 네트워크가 켜진 경우에만.
- 음성 메모(STT, SC-230): `Mode.ON_DEVICE`. 최소 호출 하나로 에뮬레이터 동작과 한국어 지원을 확인. 사용자가 [말하기]를 누를 때만 시작, 최종 결과만 보여 주고 [저장] [다시 말하기]. 저장하지 않은 텍스트는 보관하지 않는다.
- 동작하지 않으면 음성 카드를 비활성화하고 "음성 사용이 꺼져 있거나 사용할 수 없어요" 표시.

### Phase 12. SC-290 가상 보험사 전송

- 목표: 보험사 B2B 연계 시연.
- 작업: "시연용 가상 보험사" 배지, 항목별 선택, [보내기]를 눌러야 전송, 전송 로그, 접수 번호 표시.
- 규칙: 실제 보험사로 보내지 않는다. 목업 방식(앱 내부 가짜 응답 또는 자체 제작 목업 주소)은 시작 전에 사용자와 합의한다. 키·비밀값 없음.
- 확인: 항목을 끄면 전송 내용과 로그에서 빠진다.

### Phase 13. SC-280 다음 장소 안내

- 시작 전 **반드시 사용자와 합의**한다. NaviHelper에는 장소 검색 API가 없어 후보 장소 좌표를 어디서 가져올지 결정이 필요하다(`docs/sdk/navi-helper.md` 참조).
- 최소 호출: `initialize` 연결 성공/실패 확인 → `requestRoute()` 한 건.
- 연결 실패·오류 시 SC-280 버튼을 비활성화하고 이유를 표시. 동작하지 않으면 기록하고 이 Phase는 "확인 불가"로 종료한다.

### Phase 14. 나머지 화면과 제출 준비

- SC-500, 510, 520 등 P1 기타 화면을 SC-210 템플릿과 스타일 가이드로 만든다.
- 제출 전 개발자 도구 진입점(`AppPage.DEV_TOOLS`, 홈의 [개발자 도구] 버튼, `SampleApp`의 `BuildConfig.DEBUG` 분기)을 제거하고, 제출 APK(릴리스)에 노출되지 않는지 확인한다. 동의 초기화 버튼도 함께 제거한다.
